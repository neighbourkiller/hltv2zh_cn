## 1. 目标与取舍

继续使用当前翻译引擎，把旧版 NEXT 1.7.0 作为场景和词条参考。先修复动态更新边界，再补高频页面，最后完善安装、更新和发布。每次迭代独立构建、验证、记录，不把全部工作压进一个版本。

当前已经覆盖比赛、赛事、选手、战队、统计和排名的大量固定界面。本方案承接现有实现，不重做最初的引擎与目录结构。

保持以下约束：

- 只翻译固定界面，保护实体、正文、用户输入、数值、URL 和筛选参数。
- 不合并旧版全局子串管道，不覆盖网站容器的 innerHTML。
- 保留用户明确指定的术语和地图中文默认值；修订词条需有记录。
- 地图继续支持全站完整词条匹配和独立开关；优化不能缩减已约定能力。
- 构建产物仍为单文件，无后端翻译服务。
- 区分源码实现、夹具回归、实页临时运行、真实管理器安装四类证据。

旧方案中的初始调研状态不能当作当前状态。实施时以最新覆盖矩阵、源码及本次实页采样为准。

## 3. 阶段 A：建立可追踪的遗漏清单

### I01 — 旧版规则逐项归类

新增 `docs/旧版规则迁移清单.md`，按功能块整理，避免机械统计字符串数量。每项包含：ID、旧版位置、原文或模板、所属页面、当前对应规则、状态、实页证据、测试位置、优先级。

状态统一为：已覆盖、部分覆盖、待核验、待迁移、有意不迁移。有意不迁移需要说明原因，例如正文、实体或破坏节点的处理方式；可以迁移文案而舍弃旧实现。

优先审查：比赛 tooltip、推荐比赛空状态、统计表头及解释、论坛分类、独立转会文案。不得把“旧脚本包含词条”直接判为“旧版实页有效”。

### I02 — 建立可复现样本

从正常可访问页面读取目标区域，记录路由、日期、页面状态、触发操作及预期翻译。保存脱敏最小 DOM，保留嵌套 Text、属性和交互结构，移除账号信息、广告及无关大段配置。

比赛覆盖未开始、进行中和已结束；列表覆盖有结果和空状态；资料覆盖不同实体与缺失数据。实际无法取得的状态列为待验证，不伪造实页证据。

### I03 — 建立性能基线

对当前版和旧版使用相同夹具、浏览器、视口、操作序列及测量窗口，分别运行，禁止同时启用。场景包含初次扫描、1,500 个节点插入、原 Text 高频更新、长表格、静置及字段争夺。

预热后至少重复 5 次，记录中位数、尾部耗时、文本收敛时间、脚本写入次数、处理节点数及可归因长任务。两版翻译范围不同，必须同时记录正确覆盖与误翻，不能单用速度判胜负。真实站点数据另列，避免将网络、广告与夹具数据混合。

交付门槛：高频迁移项有明确状态；性能样本可重复执行；冻结同环境基线结果。此阶段不要求旧版全站实页安装。

## 4. 阶段 B：动态机制与保护，0.1.12

### I04 — 受控处理语义属性变化

涉及 `src/core/runtime.ts`、页面规则及新增运行时测试。

先用失败用例复现 class 改变后规则归属变化。为实证区域声明观察范围和影响方式：直属元素变化只处理本身；祖先状态改变影响后代时，重新处理对应子树。需要同时识别进入和离开目标状态，必要时使用 attributeOldValue。

不让每次 class 修改都扫描 body；不将动态比分闪烁、动画类加入处理范围。仅在证据表明 href 或其他属性影响规则保护时，增加相应局部观察。

验收：目标文本进入适配区后翻译、离开后恢复；祖先切换可覆盖受影响后代；无关 class 变化不触发全页扫描；原监听器和节点不变。

### I05 — 限流结束后自动恢复

涉及 `src/core/engine.ts`、`runtime.ts`、`scheduler.ts`。

引擎向运行时报告字段的下次可重试时间。由有界、去重的延迟任务统一调度，避免每次拒绝写入都创建新定时器。到期重新读取当前内容再处理，不保存待写入的旧译文。

断开节点、停用模块及 runtime.stop 时取消或丢弃任务；再次发生争夺时重新限流，避免无限紧密重试。任务上限和溢出策略需写入代码及测试。

验收：网站最后一次写入后即使没有新事件，冷却结束也能翻译；不会覆盖后来的新文案；重复触发不增加无界定时器；停止后不再写入。

### I06 — 地图规则与实体保护

涉及 `src/adapters/maps.ts`、`core/engine.ts`、`core/guards.ts`。

给地图规则增加廉价的完整词条候选判断，减少普通英文文本上的保护与选择器开销。源文恢复逻辑必须先于快速跳过：已经翻译的地图节点在停用或移入保护区时仍应恢复。

补充 Train、Ancient 等与实体同名的测试，覆盖队伍/选手链接、普通 UI、正文、标题属性和动态节点。通过明确的实体结构保护处理冲突，避免新增有限名称黑名单。

验收：已约定全名与缩写的地图翻译不减少；实体反例不误译；英文偏好、独立开关和 option 原值均保持；与冻结基线比较无新增明显长任务。

### I07 — 性能优化按测量决策

若基线显示规则搜索占主要耗时，再按 target、模块或选择器组建立索引。必须保留规则优先级及“未匹配继续尝试”的行为。没有可测收益时，不为结构美观增加索引层。

建议将同环境关键耗时恶化超过 20% 作为调查触发线，而非跨机器硬门槛。单批 6ms 是调度目标，不承诺每批都低于 6ms；超出预算需定位单节点处理成本。

阶段门槛：针对性用例与完整 `npm run check` 通过；匹配、原文恢复、限流和开关行为无回退；采样实页的原站操作正常。

## 5. 阶段 C：高频页面覆盖，0.1.13

### I08 — 比赛详情补齐

优先核对比分统计表头、经济调整指标、MVP/投票状态、直播与推荐比赛空状态、展开后的 tooltip。按真实出现的槽位添加规则，必要时新建比赛详情适配器，避免继续堆入公共规则。

长 tooltip 使用完整句式或明确模板。保留数字、版本和统计分母；统一每回合与每场的区别。原站生成的 tooltip 容器必须保留。

### I09 — Stats 专属控件

依据迁移清单选择最常用的未覆盖统计路由，补筛选、表格、展开说明、分页及空状态。对同结构共用控件复用规则，对不同布局分别采样，不以 /stats 全部归类就声明全部覆盖。

阶段门槛：选定样本内已登记的固定 UI 漏译项清零；实体、比分、日期与筛选值无变化；筛选、分页、排序、tooltip 原站操作通过。未知句式继续显示原文，并列入未覆盖清单。

## 6. 阶段 D：独立转会及低频模块，0.1.14 起

### I10 — 独立转会页面

区分战队资料中的转会表与独立转会列表/详情，补专属路由、模块开关和脱敏夹具。优先处理状态、筛选、日期、加入/离队/替补等固定结构。

跨节点句子只改可确定的 UI Text；名字和链接保留。仅靠修改 Text 无法自然表达的结构，单独设计并验证，不复制旧版 appendSuffix 或父容器重写。

### I11 — VRS 预测/模拟器与 Fantasy

先采样正常打开和操作后的状态，再判断是否进入本次发布。翻译字段标签、提示和结果说明，保留模拟参数、计算结果及原站交互。

不接管计算，不代用户提交阵容或保存账号配置。无法正常访问的功能保持待核验，并允许整个模块延后发布。

阶段门槛：每个新增模块独立开关可用；模拟或筛选前后的输入与输出数值一致；换数据、空状态及动态生成节点均验证。

## 7. 阶段 E：安装与发布，0.2.0

### I12 — 真实 Tampermonkey 验收

用构建产物完成新装、从 0.1.11 覆盖升级、刷新、关闭重开页面、配置持久化及回退验证。确认只启用一份脚本。

至少检查首页、比赛列表、三种比赛详情状态，以及本次变动模块。用户现用浏览器优先；其他浏览器仅在实际验证后列为支持环境。

临时执行脚本只能证明当前页面行为，不能替代上述验收。登录态下以读取和不提交的交互为主。

### I13 — 发布、更新与回退

建立发布清单，校验版本、元数据、产物一致性、变更说明及上一版回退产物。实际发布前再核对分发平台的现行要求。

分发渠道可选项目托管地址或 Greasy Fork；确认真实地址后才写 updateURL/downloadURL，不使用旧作者地址或占位地址。没有确定渠道时，先完成离线可安装版本，保持手动更新说明。

对已有本地安装保留当前名称、namespace 和配置键；若分发平台改变更新行为，需先做升级测试。回退同时检查配置 schema 兼容性，不能仅验证旧 JS 能启动。

发布门槛：完整检查通过；真实管理器安装证据齐全；发布范围内无已知数据损坏、交互损坏或关键实体误翻；未覆盖项明确；安装、更新和回退说明可执行。

## 8. 暂不纳入首轮

- 无刷新跨路由适配：当前只确认启动时识别路由。待实页证明有该导航方式后再实现，避免提前侵入 history。
- 菜单无刷新切换：可改善输入保留体验，但还需处理菜单标题与引擎恢复；暂不混入动态修复版本。
- 全文机器翻译、云端词库、自动上传漏译内容、独立设置后台：超出本项目当前目标。
- 大规模重构所有选择器：优先修复有样本支撑的问题。

## 9. 每个版本的完成定义

1. 改动可追溯到迁移项、问题样本或明确需求。
2. 测试验证真实失败模式，不只复制实现中的词典。
3. `npm run check` 通过，新增实页交互单独记录。
4. 更新覆盖矩阵、术语规范、验收记录、README 与 CHANGELOG 的相关部分。
5. 构建产物与版本一致，保存可回退版本。
6. 报告清楚区分已实现、已测试、已安装和待验收。

建议从 I01–I06 开始，首个代码迭代发布 0.1.12。先完成动态可靠性，再持续迁移词条；不要以词条数量或版本数量作为完成指标。
